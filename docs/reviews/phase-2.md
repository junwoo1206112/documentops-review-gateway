# Phase 2 전문가 A·B·C 교차 검증

대상: 결정론적 파서, 근거 검증, 8개 규칙 엔진, DB 없는 파이프라인, `app.inspect` CLI
기준: 정상 문서는 필드·근거와 함께 `PENDING_REVIEW`, 오류 문서는 정확한 `rule_id`와 함께 `HOLD`

## 판정 요약

| 관점 | 판정 | 근거 |
|---|---|---|
| A. 채용·실무 | 조건부 통과 → 반영 | 화면이 없어 Phase 2 결과를 사람에게 보여 줄 수단이 없었다. `app.inspect`를 추가했다. |
| B. AI/ML 시스템 | 개선 필요 → 반영 | 형식 오류 필드의 "값" 표현과 파생 총액이 필수값 검사에서 누락으로 오판됐다. |
| C. QA·신뢰성 | 개선 필요 → 반영 | 연쇄 억제가 수량 0에서 깨졌고, 메시지 순서가 set 순회에 의존해 비결정적이었다. |

## 검증에서 실제로 잡힌 결함

| # | 결함 | 영향 | 조치 |
|---|---|---|---|
| D-1 | 수량 `0` 문서가 `INVALID_MONEY`와 `LINE_TOTAL_MISMATCH`를 **동시에** 냈다. | 원인 하나에 HOLD 사유가 2개. "왜 보류됐는지"가 흐려지고 규칙 일치율이 떨어진다. | 해석 실패·범위 위반 경로를 `invalid_paths`로 모아, 그 값을 쓰는 산술 관계를 건너뛴다. 테스트로 고정. |
| D-2 | 파생 총액(`derived`)은 `value_text`가 없어서 `MISSING_REQUIRED(total)`로 오판됐다. | 근거 없음 시나리오가 "필수값 누락"으로 둔갑해 `MISSING_EVIDENCE`를 평가할 수 없었다. | 필수값 판정을 `value_text is None and value is None`으로 바꿨다. |
| D-3 | 문서번호 패턴 위반 값이 정규화 문자열로 남아 EM에서 정답(`null`)과 어긋났다. | 생성기와 파서가 서로 다른 정답 규칙을 가졌다. | "패턴 위반 값은 필드 값이 아니다"로 계약을 고정하고 양쪽을 수정했다. |
| D-4 | INVALID_MONEY 메시지 순서가 `MONEY_FIELDS` 집합 순회에 의존했다. | 같은 입력에서 메시지 순서가 달라져 감사·리포트 비교가 어려워진다. | 필드 계약 순서(`FIELD_KEYS`)로 고정했다. |
| D-5 | 생성기의 필수값 누락 루프가 `doc_date`라는 없는 속성을 지워, 날짜 누락 문서가 정상 문서로 생성됐다. | 데이터셋 카테고리와 실제 내용이 불일치. | 속성명(`date_raw`)을 고치고, 데이터 테스트가 상태 분포를 검사한다. |

## A. 채용·실무

| # | 발견 | 조치 |
|---|---|---|
| A-1 | Phase 2 산출물은 CLI로만 확인 가능한데, 그 CLI가 없으면 면접에서 "돌아간다"를 보여 줄 수 없다. | `python -m app.inspect <file>` 추가. 상태·필드·span·이슈를 한 화면에 출력한다. |
| A-2 | 8개 규칙 ID가 코드에만 있으면 설명이 어렵다. | CLI가 `INVALID_DOC_NO (doc_no): …`처럼 ID·경로·메시지를 함께 보여 준다. |
| A-3 | 규칙이 7개에서 8개로 늘어난 이유가 인수인계 문서와 다르다. | 이 문서의 D-3과 Phase 2 로그에 근거를 남겼다(문서번호 패턴 미검증은 안전 게이트의 구멍). |

## B. AI/ML 시스템

| # | 발견 | 조치 |
|---|---|---|
| B-1 | `MISSING_EVIDENCE`를 "값이 없음"과 구분하지 않으면 지표가 오염된다. | 근거 상태를 `verified`/`derived`/`missing` 3값으로 고정하고, 규칙은 마지막 두 개만 HOLD로 본다. |
| B-2 | 산술 규칙이 부분 파싱 실패에서 조용히 다른 규칙을 만들 수 있다. | 각 관계는 **필요한 값이 모두 해석된 경우에만** 평가한다. 하나라도 없으면 그 관계는 건너뛰고, 원인 규칙만 남긴다. |
| B-3 | 규칙 판정이 문서 순서(중복)에 의존한다. | 평가는 manifest 순서, 운영은 접수 순서로 고정. 재검증 API를 Phase 3에 둔다. |
| B-4 | 정답률을 "규칙 일치"로만 보면 값 오류를 놓친다. | Phase 4에서 필드 EM·문서 EM·근거 유효율을 별도로 계산하도록 파이프라인을 재사용 가능하게 분리했다(`process_document`). |

## C. QA·신뢰성

| # | 발견 | 조치 |
|---|---|---|
| C-1 | 레이아웃을 해석할 수 없을 때 추측하면 안 된다. | `DocumentFormatError` → HTTP 422(`E_UNPROCESSABLE`)로 끝낸다. 규칙 위반(HOLD)과 입력 형식 오류(422)를 분리했다. |
| C-2 | `validate()`가 쓰지 않는 `raw_text`를 받고 있었다. | 시그니처에서 제거. 근거 검증은 `apply_evidence`에서 끝난다. |
| C-3 | CRLF 문서에서 span이 어긋날 수 있다. | CRLF 문서 테스트를 추가했고, 오프셋은 원문 그대로 계산한다. |
| C-4 | 파서가 "verified"라고 해도 신뢰하면 안 된다. | `apply_evidence`가 모든 필드를 원문과 다시 대조하고, 불일치면 `missing`으로 낮춘다. 변조 span 테스트로 확인. |
| C-5 | 중복 판정에서 반려 문서를 어떻게 볼지 불명확했다. | `REJECTED`는 중복 대상에서 제외. 테스트로 고정. |

## 남은 위험

- 파서는 레이아웃 1종만 지원한다. 헤더 순서·표 형식이 달라지면 422로 끝난다(추측하지 않음).
  이는 의도된 보수적 선택이며, docs/evaluation.md `limitations`에 적는다.
- 규칙 8개는 모두 blocking이다. warning 규칙은 Phase 4 이후에도 넣지 않는다(데모 판정 흐림).
