# Phase 4 전문가 A·B·C 교차 검증

대상: 평가 엔진(`app/evaluate.py`), 리포트 스키마, CLI, `/api/evaluation/latest`, `/evaluation` 화면
기준: 고정 데이터셋에서 같은 결과가 나오고, 실패 사례 3건이 재현 테스트와 연결됨

## 판정 요약

| 관점 | 판정 | 근거 |
|---|---|---|
| A. 채용·실무 | 통과 | 한 화면에서 지표 분모·공개 사례·한계를 함께 읽을 수 있다. "정확도 100%" 문구는 쓰지 않는다. |
| B. AI/ML 시스템 | 조건부 통과 → 반영 | "실패 사례"의 의미가 지표 회귀와 혼동될 수 있었다. `failures`(공개 HOLD 사례)와 `regressions`(기준선 이탈)를 분리했다. |
| C. QA·신뢰성 | 개선 필요 → 반영 | 지표 리포트 템플릿이 중첩 지표에서 500을 냈다. 테스트가 잡았고, 렌더 구조를 고쳤다. |

## 검증에서 실제로 잡힌 결함

| # | 결함 | 영향 | 조치 |
|---|---|---|---|
| D-1 | `/evaluation`가 `field_exact_match` 하위 지표를 `metric.value`로 렌더하려다 `UndefinedError`로 500. | 리포트가 있어도 평가 화면이 깨진다. CI에서 `/evaluation` 200 테스트가 없으면 놓친다. | 중첩 지표 전용 행(`└ 필드`)을 만들고, API·화면 테스트를 추가했다. |
| D-2 | "실패 사례 3건"을 지표 회귀 3건으로 해석하면, 기준선이 완벽할 때 빈 목록이 되어 요구를 못 채운다. | 공개 요구(왜 HOLD인가)와 회귀 감지가 뒤섞인다. | `failures` = 자동 승인되지 않은 대표 3건(why/next 포함), `regressions` = 기대와 다른 문서. CLI는 `regressions`가 있을 때만 exit 1. |
| D-3 | 근거 유효율 분모를 "추출된 필드"로 두면 파싱 실패(null) 필드가 분모에 들어가 왜곡된다. | 형식 오류 문서가 근거 품질을 나쁘게 보이게 한다. | 분모를 "값이 해석된(null 아님) 필드"로 고정. 410/412, 부족 2건은 의도된 파생 총액. |
| D-4 | 문서번호 정답이 null인 문서(형식 오류)를 EM에서 어떻게 볼지 모호했다. | 형식 오류를 "값을 남기는" 추출기가 EM에서 이길 수 있다. | null 대 null만 정답. 36/36은 "형식 오류를 값으로 승격하지 않았다"는 증거다. |

## B. AI/ML 시스템

| # | 발견 | 조치 |
|---|---|---|
| B-1 | 지표를 제품 경로와 다른 코드로 계산하면 평가와 데모가 갈라진다. | `process_document`를 그대로 호출한다. 평가 전용 파서·규칙은 없다. |
| B-2 | 필드 EM은 필드별 분모가 다르면 비교가 어렵다. | 스칼라 36 고정, 품목은 `Σ max(정답,추출)`. 51셀. macro와 문서 EM을 함께 본다. |
| B-3 | HOLD 재현율만 높이면 오보류가 숨는다. | `false_hold_rate`를 항상 같은 표에 두고, 둘 다 분모를 표기한다. |
| B-4 | 근거 유효율이 1.0이 아니면 "정확도 100%"와 모순처럼 보인다. | 2건이 파생 총액임을 README·화면·리포트에 명시. 값 정확도와 근거 가능성을 분리해 설명한다. |
| B-5 | p95를 성능 주장으로 오해할 수 있다. | 36건 표본·환경 의존을 limitations와 화면에 명시하고, README에는 수치를 옮기지 않는다. |

## C. QA·신뢰성

| # | 발견 | 조치 |
|---|---|---|
| C-1 | 리포트 결정론: 시각이 들어가면 매번 달라진다. | `measurement`만 비결정적이며, 테스트가 이를 제거한 뒤 전체 JSON 동등성을 검사한다. |
| C-2 | CLI가 조용히 0으로 끝나면 CI가 회귀를 통과시킨다. | `regressions` 비어 있지 않으면 exit 1, 데이터셋 없음은 exit 2. 테스트로 고정. |
| C-3 | 리포트 파일이 없거나 깨졌을 때 API가 500이면 안 된다. | 404 + 안내 메시지. 화면은 "아직 리포트가 없습니다"와 실행 명령을 보여 준다. |
| C-4 | 평가가 데이터셋을 수정하면 안 된다. | 평가는 읽기만 하고, 임시 DB도 만들지 않는다(파이프라인 순수 함수). |
| C-5 | 테스트가 환경 변수를 지워 subprocess를 깨뜨릴 수 있다. | `os.environ` 복사 + `PYTHONIOENCODING`만 덮어쓴다. |

## A. 채용·실무

| # | 발견 | 조치 |
|---|---|---|
| A-1 | "0.995"만 보이면 실패처럼 읽힌다. | 화면에 "부족 2건 = 의도된 파생 총액"을 README에 적고, 사례 카드에서 `why`를 원문 이슈 메시지로 보여 준다. |
| A-2 | 실패 사례가 표로만 있으면 읽기 어렵다. | `입력 → 실제 → 왜 → 다음` 4줄 카드로 렌더. |
| A-3 | "정확도" 한 단어로 축약될 위험. | 화면 제목을 "정확도 하나로 말하지 않습니다"로 고정하고, 모든 지표에 분모를 붙였다. |

## 남은 위험

- 지표는 합성 36건 기준이다. 실제 문서 분포·OCR·다중 레이아웃은 측정하지 않았다.
- `failures` 3건은 데이터셋 카테고리에서 기계적으로 고른 대표 사례다. 더 많은 사례를 원하면
  리포트에 전체 HOLD 목록을 추가해야 한다(현재는 3건으로 제한).
- 평가 데이터가 바뀌면 기준선 숫자도 바뀐다. `DATASET_VERSION`이 함께 바뀌므로 과거 수치와
  직접 비교하지 않는다.
