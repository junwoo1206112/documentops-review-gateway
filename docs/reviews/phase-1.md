# Phase 1 전문가 A·B·C 교차 검증

대상: 합성 문서 36건, 정답 JSON 36개, `manifest.jsonl`, 거래처 레지스트리, 생성기
기준: Phase 1 완료 기준 — 파일 수·해시·정답 스키마 검증, 모든 값이 합성값

## 판정 요약

| 관점 | 판정 | 근거 |
|---|---|---|
| A. 채용·실무 | 통과 | `fixtures/*/README.md`만 읽어도 시연 순서와 데이터 구성을 알 수 있다. |
| B. AI/ML 시스템 | 조건부 통과 → 반영 | 오류 문서의 "정답 필드 값" 정의가 없으면 지표가 구현자마다 달라진다. 계약에 고정했다. |
| C. QA·신뢰성 | 개선 필요 → 반영 | 36건 집계를 손으로 세다가 분모를 틀렸다. 테스트와 문서를 함께 고쳤다. |

## B. AI/ML 시스템 엔지니어

| # | 발견 | 조치 |
|---|---|---|
| B-1 | `INVALID_DATE`/`INVALID_MONEY` 문서에서 그 필드의 정답 값이 무엇인지 계약이 없었다. 원문 문자열을 정답으로 볼지, `null`로 볼지에 따라 EM이 크게 달라진다. | "형식 오류로 파싱 실패한 필드의 정답은 `null`. 원문 문자열을 값으로 남기면 오답"으로 evaluation.md에 고정했다. |
| B-2 | 근거 없는 값을 만드는 경로가 데이터에 없으면 `MISSING_EVIDENCE` 규칙을 평가할 수 없다. | 총액 줄을 생략하고 `※ 총액은 …` 주석으로 파생값을 만드는 2건을 넣고, 파서 계약(파생 → `derived`)을 schema.md에 명시했다. |
| B-3 | 부가세 반올림(10% half-up) 경로를 데이터가 한 번도 지나가지 않으면 규칙 3이 미검증 상태로 남는다. | `1,234 × 3 = 3,702` → 부가세 `370`(370.2 반올림)인 정상 문서 1건을 넣었다. |

## C. QA·신뢰성

| # | 발견 | 조치 |
|---|---|---|
| C-1 | **실제 오류:** 평가 문서의 양성/음성 분모를 20/16으로 적었지만, 중복 첫 건이 `PENDING_REVIEW`라서 실제로는 **19/17**이다. HOLD 재현율이 조용히 틀릴 수 있었다. | 문서의 분모·예시 리포트를 19/17로 수정하고, 테스트에 상태 분포(17/19)를 고정했다. |
| C-2 | Windows에서 `git autocrlf`가 켜져 있으면 `.txt`가 CRLF로 바뀌어 SHA-256이 달라진다. | `.gitattributes`로 `*.txt`, `*.jsonl`, `*.json`을 LF 고정. 테스트가 CRLF 혼입을 검사한다. |
| C-3 | 데이터를 손으로 고치면 manifest 해시만 맞고 정답은 어긋날 수 있다. | 생성기 `--check` 재생성 비교를 테스트에 넣었다(부분 수정 즉시 실패). |
| C-4 | "모든 값이 합성"이라는 주장은 검사 없이는 문구일 뿐이다. | 주민번호·휴대전화·이메일·계좌번호 정규식 검사를 데이터 전체에 추가했다. |
| C-5 | 품목 행이 "2칸 이상 공백" 계약을 지키는지 확인하지 않으면 Phase 2 파서가 바로 깨진다. | 품목 행 형식과 값 일치를 데이터 테스트로 고정했다. |
| C-6 | 파생 총액 문서에 정답 span을 넣으면 "근거 없음" 시나리오가 무너진다. | 파생·누락 필드는 `evidence` 키를 생략하도록 정답 스키마와 테스트를 맞췄다. |

## A. 채용·실무

| # | 발견 | 조치 |
|---|---|---|
| A-1 | 36개 파일만 덩그러니 있으면 무엇부터 열어야 할지 모른다. | `fixtures/evaluation/README.md`(읽기 전용 규칙)와 `fixtures/demo/README.md`(4장면 순서)를 추가했다. |
| A-2 | 거래처 이름이 실제 회사와 겹칠 수 있다는 오해를 막아야 한다. | `vendors.json`에 "모두 가상의 이름" 주석을 넣고, 보안 문서에도 같은 문구를 두었다. |
| A-3 | 하루 만에 만든 합성 데이터는 "실제 데이터처럼 보이는가"를 보여 줘야 한다. | 문서 레이아웃을 실제 거래명세서와 유사하게(헤더 4줄 + 품목표 + 합계 3줄) 유지했다. 금액·수량·부가세는 현실적인 범위다. |

## 남은 위험

- 합성 문서는 레이아웃이 1종류다. 실제 문서처럼 헤더 순서·표 형태가 흔들리면 파서가 깨진다.
  MVP는 이 한계를 `limitations`에 적고, 레이아웃 변형은 Phase 4 이후 과제로 둔다.
- 문서 수가 36건이라 p95는 표본이 작다. 성능 주장에는 쓰지 않는다.
