# Phase 14 전문가 A·B·C 교차 검증

대상: Gate A 결정에 따른 필드 단위 사람 수정(원문 재인용), 재검증 연동, append-only 수정 이력
기준: P-003 수용 기준 — 근거 없는 수정 차단, 수정 후 재검증, 감사 불변, 기존 36건 기준선 불변

## 판정 요약

| 관점 | 판정 | 근거 |
|---|---|---|
| A. 제품·인수 | 통과 | HOLD 문서에서 원문을 재인용해 값을 고치고, 자동 승인 없이 검토 대기로 돌아오는 흐름을 화면에서 확인했다. |
| B. 정확성 | 개선 반영 | 수정값이 `fields`를 덮어쓰면 추출 원본·감사가 훼손된다. `fields`(추출 원본)와 `effective_fields`(수정 반영)를 분리했다. |
| C. QA·검증 | 개선 반영 | 수정 API·UI·재검증·감사 불변·모호한 인용·종료 상태까지 14개 테스트로 고정했고, 155 passed를 확인했다. |

## Gate A 결정 요약 (2026-11-26)

1. 근거: **원문 재인용만**. 원문에 없는 값은 만들 수 없다.
2. 수정 후 상태: **항상 재검증**, 자동 승인 없음.
3. 감사: 수정 전/후·span·검토자·사유 영구 보존(append-only).
4. 권한: `reviewer_alias` 유지, 인증(P-006)은 범위 밖.

전문가 검증에서 나온 핵심 지적: 로드맵의 "원문 재인용" 기본안은 `MISSING_REQUIRED`를
**해소하지 못한다**(원문에 값이 없으므로 인용할 대상이 없다). 이 모순을 숨기지 않고
ADR 0003에 명시적 제약으로 남겼다. 누락 필드는 여전히 재업로드가 정답이다.

## B. 정확성

| # | 발견 | 조치 |
|---|---|---|
| B-1 | 수정값도 기존 규칙 엔진·`apply_evidence`를 통과해야 한다. | 수정 필드를 `verified` span으로 주입한 뒤 전체 규칙을 재실행한다. |
| B-2 | 수정이 중복·산술 판정을 바꿀 수 있다. | 수정 후 `duplicate_of`와 모든 이슈를 재계산하고, 이전 open 이슈는 resolved로 닫는다. |
| B-3 | 수정 이력이 여러 번 쌓이면 최신값만 유효해야 한다. | path별 마지막 수정만 effective에 적용하고, 전체 이력은 보존한다. |
| B-4 | `MISSING_REQUIRED`를 수정으로 해소할 수 있다고 오해할 수 있다. | 원문에 값이 존재할 때만 가능하며, 없으면 422·재업로드라는 제약을 ADR·룰 문서·UI에 명시. |

## C. QA·검증

| # | 발견 | 조치 |
|---|---|---|
| C-1 | 수정 API의 입력 검증이 여러 계층에 흩어질 수 있다. | Pydantic(형식) + 서비스(도메인)로 나누고, 422 코드를 통일했다. |
| C-2 | 종료 상태에서 수정이 가능하면 감사가 모순된다. | `APPROVED`/`REJECTED`는 409. |
| C-3 | 수정 후 승인이 자동으로 되면 계약 위반이다. | 수정은 `PENDING_REVIEW`까지만. 승인 테스트를 별도로 수행. |
| C-4 | 평가 기준선이 바뀌면 Phase 14가 회귀를 숨긴다. | 평가셋은 수정을 사용하지 않으며, 36건 기준선(36/36·19/19·0/17·410/412)을 전체 테스트로 재확인. |
| C-5 | 화면 폼이 실제로 동작하는지 API 테스트만으로는 부족하다. | 폼 POST→303→이력 표시를 UI 테스트로 고정했고, 브라우저에서 `가온상사(주) → 가온상사` 수정·`PENDING_REVIEW` 전환·감사 이벤트까지 직접 확인했다. |
| C-6 | 스크린샷 파일이 JPEG 바이트인데 `.png` 확장자로 커밋되어 MIME이 어긋났다. | GitHub/브라우저가 잘못된 Content-Type으로 서빙할 수 있다. | `docs/images/*.jpg`로 이름을 바로잡고 README 링크를 갱신했다. |

## A. 제품·인수

| # | 발견 | 조치 |
|---|---|---|
| A-1 | 수정 폼이 "무엇을 고칠 수 있는지"를 알려 주지 않으면 추측하게 된다. | 필드 선택에 현재 값을 함께 표시하고, 원문 재인용 필수·자동 승인 없음·누락 필드 재업로드를 문구로 고정. |
| A-2 | 수정 후 원본과 수정값을 구분해 보여 줘야 감사가 읽힌다. | 필드 행에 `사람 수정` 배지, `원본 X`, 수정 이력 표(근거 span 포함)를 표시. |
| A-3 | "고칠 수 있다"는 기능이 "근거 없이 승인할 수 있다"로 오해될 수 있다. | README·ADR·UI 모두 "원문에 있는 값만, 승인은 별도"를 반복해 명시. |

## 남은 위험

- 스칼라 6개 필드만 지원한다. 품목 수정은 후속 Gate/페이즈가 필요하다.
- 원문에 없는 누락 값은 해소할 수 없다(의도). 재업로드 경로가 유일하다.
- `reviewer_alias`는 인증이 아니다. 공개 배포 전 인증(P-006) 없이는 수정 API를 신뢰 경계로 쓸 수 없다.
- 수정값의 정규화는 기존 파서 규칙을 따른다. 새로운 표기(예: 한글 금액)는 별도 규칙·데이터가 필요하다.
