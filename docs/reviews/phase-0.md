# Phase 0 전문가 A·B·C 교차 검증

대상: 계약 문서(`docs/schema.md`, `docs/rules.md`, `docs/evaluation.md`), 저장소 뼈대, 계약 테스트
기준: Phase 0 완료 기준 — "새 인수자가 README만 읽고 입력·출력·HOLD 기준·비목표를 설명할 수 있다"

## 판정 요약

| 관점 | 판정 | 근거 |
|---|---|---|
| A. 채용 담당자·AI 자동화 실무자 | 조건부 통과 → 반영 후 통과 | 계약은 촘촘하지만, 첫 화면에 "무엇을 보게 되는지"가 없었다. 실행 명령도 테스트뿐이었다. |
| B. AI/ML 시스템 엔지니어 | 개선 필요 → 반영 후 통과 | 필드 EM 분모 정의가 자기모순이었고, 36건 p95의 통계적 한계 표기가 없었다. |
| C. QA·신뢰성·인수인계 | 개선 필요 → 반영 후 통과 | 문서↔코드 드리프트, README 링크, 환경 변수 누락을 잡는 기계적 테스트가 없었다. |

## A. 채용 담당자·AI 자동화 실무자

| # | 발견 | 조치 |
|---|---|---|
| A-1 | "HOLD"가 첫 화면에서 설명 없이 등장한다. 비개발 채용 담당자는 승인 대기와 구분하지 못한다. | README에 용어 정의 1줄과 `PENDING_REVIEW`/`HOLD`/종료 상태 설명을 추가했다. |
| A-2 | Phase 0 문서만으로는 60초 안에 무엇을 보게 되는지 알 수 없다. "검증·보류·승인"이 추상적으로 읽힌다. | README에 **60초 데모 시나리오 5단계**(정상→불일치→중복→승인→422/409)를 추가했다. 실제 화면은 Phase 3에서 붙지만, 계약이 먼저 고정된다. |
| A-3 | API만 있고 화면 계획이 안 보이면 "백엔드 토이"로 보인다. | ADR 0002에 서버 렌더링 화면·원문/필드 나란히 보기 결정을 명시했다. |

## B. AI/ML 시스템 엔지니어

| # | 발견 | 조치 |
|---|---|---|
| B-1 | 필드 EM 분모가 "정답에 존재하는 횟수"인데 "누락 null도 포함"이라고 적혀 **자기모순**이다. 구현자가 임의로 해석하면 지표를 비교할 수 없다. | 스칼라 필드 분모를 **항상 36**으로 고정하고, 품목 분모는 `Σ max(정답 행수, 추출 행수)`로 정의했다. |
| B-2 | macro 평균이 필드 수에 따라 왜곡될 수 있는데 이유가 없다. | 금액 필드가 많은 구조에서 왜곡되지 않도록 한 선택임을 명시하고, 문서 완전 일치를 항상 함께 보도록 고정했다. |
| B-3 | 36건 p50/p95를 성능 주장처럼 읽을 수 있다. | "표본 36건, 신뢰구간 주장 없음"을 명시하고, 평가 리포트에서 `measurement`를 결정론 비교에서 제외했다. |
| B-4 | `warning` 심각도가 스키마에만 있고 미사용이면, 나중에 누가 warning 규칙을 추가했을 때 HOLD 판정에서 조용히 무시된다. | 엔진은 blocking만 집계한다는 계약을 명시하고, **MVP에 warning 규칙이 0개**임을 테스트로 고정했다. 규칙 추가 시 테스트가 먼저 깨진다. |
| B-5 | "정확도" 한 숫자로 축약될 위험. | HOLD 재현율과 오보류율을 항상 함께 보고하도록 evaluation.md에 명시했다. |

## C. QA·신뢰성·인수인계

| # | 발견 | 조치 |
|---|---|---|
| C-1 | 상태 전이가 코드와 문서에 따로 적혀 있으면 반드시 어긋난다. | `app/domain/statuses.py`를 단일 출처로 두고, `tests/test_contracts.py`가 문서 표의 전이 행을 직접 검사한다. `HOLD→APPROVED`는 코드·문서 양쪽에서 금지다. |
| C-2 | 규칙 ID·필드 키도 같은 드리프트 위험이 있다. | `app/domain/rules.py`, `app/domain/fields.py`를 단일 출처로 두고 문서 표 존재를 테스트한다. |
| C-3 | README 링크·환경 변수 예시는 조용히 깨진다. | README 로컬 링크 존재, `.env.example`의 환경 변수 커버리지를 테스트로 고정했다. |
| C-4 | 중복 판정이 접수 순서에 의존한다는 사실이 지표 해석에서 빠져 있었다. | evaluation.md `limitations`에 순서 의존성과 재검증으로 상태가 바뀔 수 있음을 명시했다. |
| C-5 | 감사 이력 append-only를 "코드에서 안 고치면 된다"로 두면 나중에 깨진다. | DB 트리거로 UPDATE/DELETE를 차단하는 결정을 schema.md·ADR 0002에 고정하고, Phase 3에서 UPDATE/DELETE 양쪽을 테스트하기로 했다. |
| C-6 | `INGESTED`가 API에 노출되지 않는 이유가 없으면 상태 모델이 미완성처럼 보인다. | "업로드 요청 한 번에서 검증까지 끝난다"를 schema.md에 명시했다. |

## 반대 검증(Contrarian) — 채택하지 않은 제안

| 제안 | 기각 이유 |
|---|---|
| 처음부터 필드 단위 사람 수정 기능 | "근거 없는 값은 승인 불가" 원칙과 충돌한다. 근거 모델을 먼저 정해야 한다(`P-003`). |
| warning 규칙 1~2개를 예시로 추가 | HOLD 판정과 무관한 경고는 데모에서 "왜 승인 가능한가"를 흐린다. Phase 4 이후로 미룬다. |
| Phase 0에서 API 스텁까지 구현 | 계약 검증 없이 코드를 늘리면 드리프트만 커진다. Phase 2에서 계약 테스트가 먼저 통과한 뒤 붙인다. |
| 평가 지표에 F1 추가 | 양성/음성 비용이 비대칭(놓친 오류 > 불필요한 검토)이라 단일 F1은 판단을 흐린다. 재현율·오보류율을 분리 보고한다. |

## 남은 위험

- 계약 테스트는 "문서에 문자열이 있는지"를 본다. 문서의 **의미**가 코드와 맞는지는 Phase 2의
  규칙 단위 테스트가 담당한다.
- Phase 0 시점에는 실행 가능한 제품 경로가 없다. 이는 의도된 순서이며, Phase 2 완료 전까지
  README의 "현재 상태" 표가 이를 정직하게 표시한다.
