# Phase 3 전문가 A·B·C 교차 검증

대상: SQLite 스키마, append-only 감사, ReviewService, REST API 8개, 서버 렌더링 화면 6개
기준: 사람이 원문 근거를 보고 판정하며, 사유 없는 승인과 `HOLD` 직접 승인이 코드·화면에서 모두 차단됨

## 판정 요약

| 관점 | 판정 | 근거 |
|---|---|---|
| A. 채용·실무 | 통과 | 실제 브라우저에서 업로드→HOLD→원문 하이라이트→감사 이력까지 한 화면 흐름으로 확인했다. |
| B. AI/ML 시스템 | 조건부 통과 → 반영 | 재검증이 기존 이슈를 "해소"로 남기는지, 중복 판정이 사슬로 이어지는지 계약이 필요했다. |
| C. QA·신뢰성 | 개선 필요 → 반영 | 동시 판정 시 상태 전이 검사가 TOCTOU로 뚫릴 수 있었다. 조건부 UPDATE로 막았다. |

## C. QA — 실제로 고친 결함

| # | 결함 | 영향 | 조치 |
|---|---|---|---|
| D-1 | 판정 전 상태를 읽고 나서 UPDATE하는 사이에 다른 요청이 끼어들면, 두 요청이 모두 전이 검사를 통과할 수 있다(TOCTOU). | 같은 문서에 승인 2건, 또는 승인+반려가 동시에 기록될 수 있다. 감사 이력의 신뢰가 깨진다. | `UPDATE ... WHERE id=? AND status=?`로 바꾸고 `rowcount != 1`이면 409로 롤백. 재검증도 동일. |
| D-2 | 재검증이 기존 이슈를 삭제하면 "왜 보류였는지"가 사라진다. | 감사·평가에서 과거 판정 근거를 재구성할 수 없다. | `status='open'`만 `resolved`로 닫고 새 이슈를 추가한다. 테스트가 resolved 개수를 검사. |
| D-3 | 감사 이벤트가 앱 코드에만 append-only면, 나중에 실수로 UPDATE하는 코드가 들어온다. | "immutable audit"이 문구가 된다. | SQLite `BEFORE UPDATE/DELETE` 트리거가 `RAISE(ABORT)`. 테스트가 두 경로 모두 실패를 확인. |
| D-4 | 업로드 원문을 화면에 그대로 넣으면 저장형 XSS가 된다. | 악성 `.txt` 하나로 세션을 노릴 수 있다(데모라도 신뢰 상실). | Jinja2 자동 이스케이프 + span 하이라이트도 `escape()` 후 `mark`만 삽입. CSP `default-src 'none'`. |
| D-5 | 이슈 정렬이 DB 삽입 순서에 의존하면 같은 문서의 API 응답이 달라진다. | 재현·비교가 어렵다. | `ORDER BY rule_id, path, id`로 고정. |

## B. AI/ML 시스템

| # | 발견 | 조치 |
|---|---|---|
| B-1 | 재검증 결과가 같은 상태일 때(예: 여전히 HOLD) 감사 이벤트를 남길지 불명확했다. | 상태가 같아도 `REVALIDATED`를 남긴다. "언제 다시 확인했는가"가 감사의 일부다. |
| B-2 | 중복 문서가 다시 중복의 기준이 되면 사슬이 무한히 이어질 수 있다. | 접수 순서상 **가장 먼저 일치하는 비반려 문서**를 원본으로 기록한다. `duplicate_of`는 단일 참조다. |
| B-3 | `duplicate_of`가 문서 레코드에 없으면 화면에서 원본을 추적할 수 없다. | 컬럼과 응답 필드에 추가하고, 재검증 시 갱신한다. |
| B-4 | 평가(Phase 4)가 API를 거치지 않고 같은 파이프라인을 써야 지표와 제품이 일치한다. | `process_document`를 그대로 재사용하고, DB는 평가에서 임시 파일로만 쓴다. |

## A. 채용·실무

| # | 발견 | 조치 |
|---|---|---|
| A-1 | HOLD 문서에서 승인 버튼이 왜 비활성인지 설명이 필요하다. | 폼 위에 "승인은 검토 대기 문서에만 가능, 보류는 재검증 후" 문구를 고정. |
| A-2 | "규칙 재검증" 버튼이 좁은 화면에서 두 줄로 깨졌다. | `white-space: nowrap`으로 버튼 라벨 고정. |
| A-3 | 화면에서 원문과 필드가 떨어져 있으면 "근거"가 말로만 남는다. | 좌: 원문(검증 span 하이라이트), 우: 필드·근거 상태·span 좌표·발췌문을 나란히 배치. |
| A-4 | API만 있으면 60초 데모가 불가능하다. | `/upload`, `/documents/{id}/decision`, `/documents/{id}/revalidate` 폼 경로를 추가해 JS 없이 전체 흐름을 시연. |
| A-5 | 데모 데이터를 손으로 4번 올려야 한다. | `python scripts/seed_demo.py` 추가. 순서와 결과를 콘솔에 출력. |

## 남은 위험

- 감사 이벤트 ID는 전역 AUTOINCREMENT라 문서별로 1부터 시작하지 않는다. 화면에 표시되는
  번호가 문서별 순번이 아니라는 점은 감사 로그의 정상 동작이다.
- 동시성은 조건부 UPDATE로 막았지만, SQLite 단일 파일·단일 프로세스 전제다.
  다중 인스턴스는 명시적 비목표다(ADR 0002).
- 업로드 시 중복 검사를 위해 전체 문서를 메모리로 읽는다. 36건 규모에서는 문제없고,
  대량 운영은 범위 밖이다.
