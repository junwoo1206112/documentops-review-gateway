# AI 포트폴리오 개선점 — 인수인계 실행서

작성일: 2026-11-25  
대상: AI 자동화·RPA·Agent·제조 AI 신입/인턴 지원 포트폴리오  
작성 방식: `C:\AI\ouroboros`의 specification-first 원칙과 전문가 A·B·C 교차 검증

## 0. 한 줄 목표

개인정보가 없는 합성 한국어 업무 문서를 **추출 → 근거 연결 → 규칙 검증 → 사람 승인 → 감사 추적 → 평가 공개** 흐름으로 처리하는 `DocumentOps Review Gateway`를 만들고, 기존 AI 포트폴리오의 실행 증거를 짧고 재현 가능하게 보강한다.

이 프로젝트가 보여 줄 역량은 “AI가 답한다”가 아니라 **AI 산출물을 업무에 안전하게 투입하기 위해 검증·보류·승인·추적하는 방법**이다.

## 1. 의사결정 기록과 범위

### 확정 범위

- 한국어 합성 문서 36건으로 시작한다. 문서는 거래명세서·견적서·발주서 성격의 텍스트 기반 PDF 또는 텍스트 파일이며, 실제 개인정보·실제 회사 문서를 사용하지 않는다.
- 필드: `거래처`, `문서번호`, `날짜`, `품목[]`, `수량`, `단가`, `공급가액`, `부가세`, `총액`.
- 결과 상태: `PENDING_REVIEW`, `HOLD`, `APPROVED`, `REJECTED`.
- 필수값 누락, 날짜/금액 형식 오류, 품목 합계와 총액 불일치, 중복 문서, 알 수 없는 거래처는 기본적으로 `HOLD`다.
- 모든 필드는 원문 페이지·문자 범위·발췌문을 근거로 가진다. 근거가 없는 추출값은 승인 후보가 될 수 없다.
- 승인·반려는 사람만 실행한다. 데모에는 외부 전송·결제·ERP 쓰기를 연결하지 않는다.
- FastAPI, SQLite, Docker, pytest, GitHub Actions 및 평가 화면을 포함한다.

### 비목표

- 실제 고객 문서, 주민번호·계좌·연락처 등 개인정보 처리
- 실제 OCR 정확도나 실제 기업 운영 효과 주장
- LLM의 자유 생성만으로 숫자·거래처를 확정하는 방식
- 로그인·권한 체계·멀티테넌시·클라우드 큐 등 운영용 대형 기능
- 자동 승인·외부 시스템 실행

### 의도적으로 나중에 하는 것

- 스캔 이미지 OCR은 Phase 1~4의 텍스트 기반 흐름이 검증된 뒤 Phase 5 확장으로 넣는다. 처음부터 OCR 품질 문제와 업무 규칙 문제를 한 번에 해결하려 하지 않는다.
- RAG는 문서 필드 추출에 필수가 아니다. 거래처 정책·검증 규칙 설명을 찾는 보조 기능으로만 나중에 추가한다.

## 2. Ouroboros 전문가 A·B·C 교차 검증

| 관점 | 판정 | 확인된 문제 | 반영한 권장안 |
|---|---|---|---|
| A. 채용 담당자·AI 자동화 실무자 | 조건부 통과 | “OCR·LLM·대시보드”를 모두 나열하면 일반 챗봇처럼 보이고, 실제 동작 증거가 없으면 신뢰가 약하다. | 핵심 메시지를 `검증·보류·사람 승인·감사 이력`으로 고정한다. 60초 데모, 실행 명령, 평가 수치, 실패 사례를 README 첫 화면에 둔다. |
| B. AI/ML 시스템 엔지니어 | 개선 필요 | 정확도를 하나의 숫자로만 보이면 필드 오류·근거 오류·과도한 보류를 숨긴다. OCR과 추출 모델을 초기에 묶으면 실패 원인을 알 수 없다. | 필드별 Exact Match, 문서 완전 일치, HOLD 재현율·오보류율, 근거 유효율, p50/p95 처리 시간을 분리한다. 텍스트 문서부터 시작하고 OCR은 별도 확장으로 격리한다. |
| C. QA·신뢰성·인수인계 담당 | 개선 필요 | 데이터셋 버전, 판정 규칙 버전, 상태 전이, 실패 사례가 없으면 재현·감사가 불가능하다. | 합성 데이터 manifest·정답 라벨·SHA-256·규칙 버전·감사 로그를 남긴다. CI에서 단위/통합/e2e 평가를 분리 실행한다. |

### 합의 결론

새 프로젝트는 만들 가치가 있다. 단, **“OCR Agent”가 아니라 “DocumentOps Review Gateway”**로 범위를 좁혀야 한다. 첫 출시의 성공 기준은 모델이 화려한 답을 내는 것이 아니라, 잘못되거나 불확실한 문서를 안전하게 `HOLD`하고 사람이 근거를 보고 판정할 수 있는지다.

### 반대 검증(Contrarian)에서 보류한 가정

1. “데이터베이스가 있어야 한다”는 가정: 데모와 포트폴리오에는 SQLite가 충분하다. Postgres 전환은 요구사항이 생길 때만 한다.
2. “OCR을 넣어야 AI 프로젝트다”라는 가정: 아니다. 구조화·검증·근거·승인 흐름이 핵심이며, 텍스트 추출부터 검증하는 편이 더 정직하다.
3. “자동 승인 비율이 높을수록 좋다”는 가정: 포트폴리오 목표는 안전한 보류와 검토 가능성이다. 승인 자동화는 비목표다.

## 3. 권장 아키텍처

```text
합성 문서 업로드
  → Ingestion (문서 ID, SHA-256, 텍스트, 페이지/문자 오프셋)
  → ExtractionProvider (기본: 결정론적 파서 / 선택: LLM 어댑터)
  → Evidence Mapper (필드별 원문 span·발췌문)
  → Validation Rules (누락·형식·합계·중복·거래처)
  → Review Queue (PENDING_REVIEW 또는 HOLD)
  → 사람 승인/반려 + 사유
  → Immutable Audit Log + Evaluation Report
```

### 책임 경계

| 구성요소 | 책임 | 금지 사항 |
|---|---|---|
| `ingestion` | 파일 해시, 텍스트 추출, 원문 위치 저장 | 원문을 임의로 수정하지 않음 |
| `extraction` | 정해진 스키마의 후보 값과 신뢰도·근거 후보 생성 | 승인 상태를 바꾸지 않음 |
| `validation` | 명시 규칙으로 HOLD 사유 생성 | 모델 판단을 규칙 결과처럼 위장하지 않음 |
| `review` | 사람의 승인·반려와 사유 기록 | 자동 승인하지 않음 |
| `audit` | 요청·버전·상태 전이·검토 이력 append-only 기록 | 기존 이력을 덮어쓰지 않음 |
| `evaluation` | 고정 정답 데이터로 지표·실패 사례 산출 | 운영 데이터와 시험 데이터를 혼합하지 않음 |

### 최소 데이터 모델

- `Document`: `id`, `sha256`, `source_kind`, `ingested_at`, `extractor_version`, `ruleset_version`
- `ExtractedField`: `document_id`, `field_name`, `value`, `confidence`, `page`, `char_start`, `char_end`, `evidence_excerpt`
- `ValidationIssue`: `document_id`, `rule_id`, `severity`, `message`, `status`
- `ReviewDecision`: `document_id`, `decision`, `reviewer_alias`, `reason`, `created_at`
- `AuditEvent`: `event_id`, `document_id`, `event_type`, `from_status`, `to_status`, `actor`, `metadata`, `created_at`

### 상태 전이

```text
INGESTED → PENDING_REVIEW → APPROVED
                    └────→ REJECTED
INGESTED → HOLD → PENDING_REVIEW | REJECTED
```

- `HOLD → APPROVED` 직접 전이는 금지한다. 사람이 보류 사유를 해소하고 `PENDING_REVIEW`로 되돌린 뒤 승인한다.
- 동일 `document_id + sha256` 재업로드는 중복으로 `HOLD`한다.
- 승인·반려에는 `reviewer_alias`와 1자 이상 사유가 필수다.

## 4. 구현 페이즈

### Phase 0 — 계약 고정과 저장소 뼈대

목적: 기능을 늘리기 전에 문제·데이터·판정 기준을 고정한다.

- `README.md`에 사용자 문제, 지원 범위, 비목표, 데이터 정책을 명시한다.
- `docs/schema.md`, `docs/rules.md`, `docs/evaluation.md`, `docs/adr/0001-text-first.md`를 만든다.
- API 상태 코드와 상태 전이표를 Pydantic 모델 또는 OpenAPI에 먼저 정의한다.
- 생성·검증 명령과 Python 버전을 `pyproject.toml`, `.env.example`, `Dockerfile`에 한 곳에서 관리한다.

완료 기준:

- 새 인수자가 README만 읽고 입력·출력·HOLD 기준·비목표를 설명할 수 있다.
- 실제 문서·개인정보를 사용하지 않는다는 데이터 정책이 명시돼 있다.

### Phase 1 — 합성 데이터와 고정 평가 세트

목적: 데모 데이터와 평가 데이터를 분리하고 재현 가능한 정답을 만든다.

- 합성 문서 36건과 `manifest.jsonl`을 만든다.
  - 정상 16건
  - 필수값/형식 오류 8건
  - 금액 불일치 6건
  - 중복·알 수 없는 거래처·근거 누락 등 경계 사례 6건
- 각 문서에 정답 JSON, 기대 상태, 기대 `rule_id`, 필드 근거 span을 작성한다.
- `dataset_version`, 각 파일 SHA-256, 생성 규칙을 manifest에 기록한다.
- `fixtures/demo`와 `fixtures/evaluation`을 분리한다. 테스트가 평가 정답을 수정하지 못하게 읽기 전용 관례를 문서화한다.

완료 기준:

- `pytest tests/test_dataset_manifest.py -q`가 파일 수, 해시, 정답 스키마를 검증한다.
- 데이터셋의 모든 이름·주소·번호는 합성값임을 확인한다.

### Phase 2 — 추출·근거·규칙 검증 MVP

목적: 한 문서를 구조화하고 안전하게 보류하는 핵심 흐름을 완성한다.

- `ExtractionProvider` 인터페이스를 만들고 기본 구현은 결정론적 텍스트 파서로 둔다.
- 선택적 LLM 구현은 같은 인터페이스 뒤에 두며, API 키가 없어도 CI와 데모가 동작해야 한다.
- 모든 추출 필드는 최소 하나의 `page/char_start/char_end/evidence_excerpt`를 가져야 한다.
- 룰 엔진은 다음 코드를 안정적으로 낸다: `MISSING_REQUIRED`, `INVALID_DATE`, `INVALID_MONEY`, `LINE_TOTAL_MISMATCH`, `DUPLICATE_DOCUMENT`, `UNKNOWN_VENDOR`, `MISSING_EVIDENCE`.
- 심각도 `blocking` 이슈가 하나라도 있으면 `HOLD`; 없으면 `PENDING_REVIEW`이다.

완료 기준:

- 정상 문서 1건은 필드와 근거를 보여 주며 `PENDING_REVIEW`가 된다.
- 금액 불일치·근거 누락 문서는 각각 정확한 `rule_id`와 함께 `HOLD`가 된다.
- `pytest tests/test_extraction.py tests/test_validation.py -q`가 통과한다.

### Phase 3 — 검토 UI/API와 감사 이력

목적: “사람이 최종 판정한다”는 약속을 화면과 데이터로 증명한다.

- FastAPI: 업로드, 문서 목록, 상세, 보류 사유, 승인, 반려, 감사 이력 API를 제공한다.
- 화면: 원문 발췌문과 구조화 필드를 나란히 보여 주고, HOLD 사유와 상태 전이를 표시한다.
- 승인/반려 버튼에는 검토자 별칭과 사유를 필수로 받는다.
- 모든 상태 변경은 `AuditEvent`를 추가한다. 수정·삭제 API는 MVP에서 제공하지 않는다.
- SQLite는 Docker 볼륨으로 유지하되, 데모 환경 재시작 시 데이터 초기화 가능성을 README에 쓴다.

완료 기준:

- `HOLD` 문서가 근거와 룰을 화면에서 보여 준다.
- 사람이 사유를 입력하지 않으면 승인·반려 API가 422를 반환한다.
- 감사 이력에 업로드·검증·검토 상태 전이가 시간순으로 남는다.

### Phase 4 — 평가·관측성·실패 사례

목적: 좋은 결과만 전시하지 않고 안전성과 한계를 수치로 설명한다.

- `python -m app.evaluate --dataset fixtures/evaluation` 같은 읽기 전용 평가 명령을 만든다.
- 최소 지표:
  - 필드별 Exact Match와 문서 완전 일치율
  - HOLD 재현율(문제가 있는 문서를 HOLD한 비율)
  - 오보류율(정상 문서를 HOLD한 비율)
  - 근거 유효율(인용 위치가 실제 값과 일치하는 비율)
  - 처리 시간 p50/p95
- 화면/정적 리포트에 3개 실패 사례를 공개한다. 각각 `입력 → 실제 결과 → 왜 HOLD/실패인가 → 다음 개선` 형식이다.
- “정확도”라는 단일 문구만으로 성과를 주장하지 않는다. 각 지표의 분모·데이터셋 버전·한계를 함께 표시한다.

완료 기준:

- 고정 데이터셋에서 실행할 때 같은 결과가 나온다.
- 실패 사례 3개가 재현 테스트와 연결된다.
- `pytest tests/test_evaluation.py -q`가 지표 계산과 리포트 스키마를 검증한다.

### Phase 5 — OCR 확장과 출시 준비

목적: MVP 품질을 해치지 않고 이미지 문서를 제한적으로 확장한다.

- OCR 입력은 `source_kind=scan`으로 명시하고, 텍스트 기반 문서와 지표를 섞지 않는다.
- OCR 신뢰도가 낮거나 필수 필드 근거를 찾지 못하면 자동으로 `HOLD`한다.
- OCR 성능은 별도 데이터셋·별도 표로 보고한다.
- Docker, `.env.example`, GitHub Actions, 보안·데이터 정책, 데모 스크립트를 마감한다.

완료 기준:

- `docker compose up --build` 뒤 예제 문서를 처리할 수 있다.
- GitHub Actions가 린트·단위·통합·평가 테스트를 실행한다.
- README 첫 화면에서 데모 링크, 실행법, 테스트 배지, 데이터 제한을 볼 수 있다.

## 5. 테스트·CI 계약

| 계층 | 검증 대상 | 예시 |
|---|---|---|
| 단위 | 금액 파싱, 날짜 형식, 상태 전이, 각 rule | `tests/test_validation.py` |
| 통합 | 업로드 → 추출 → HOLD/PENDING → 검토 → audit | `tests/test_review_flow.py` |
| 회귀 평가 | 고정 평가 36건의 결과 및 지표 스키마 | `tests/test_evaluation.py` |
| API | 입력 검증, 승인/반려 사유 필수, 중복 업로드 | `tests/test_api.py` |
| 수동 UX | 근거와 원문이 같은 필드를 가리키는지 | 60초 데모 체크리스트 |

GitHub Actions 최소 단계:

1. 의존성 설치
2. format/lint
3. 명시된 pytest 파일 실행
4. 평가 리포트 생성 및 artifact 업로드
5. 테스트·평가 실패 시 배포/배지 갱신 중단

주의: CI에는 비밀키·실제 문서·외부 LLM API 키를 넣지 않는다. 기본 추출기는 네트워크 없이 동작해야 한다.

## 6. 포트폴리오 마감 트랙

### Track B1 — 기존 AI 프로젝트 시연 영상

- Evidence-Gated Work Agent: 질문 입력 → 근거 충분 시 계획 → 근거 부족/충돌 시 차단 → 승인 뒤 mock 실행 → 감사 이력 순서로 45~60초.
- Smart Manufacturing ML: 데이터 검증 → 예측/이상 징후 결과 → 한계 또는 검토 지점 → 대시보드/테스트 증거 순서로 45~60초.
- 영상에는 실제로 확인한 기능만 말한다. 모델 성능, 운영 적용, 외부 연동은 검증 증거가 있을 때만 말한다.

### Track B2 — README와 CI

- README 첫 화면: 프로젝트 한 줄 가치, 아키텍처 그림, 3개 핵심 검증, 실행 명령, 테스트 배지, 데모 링크.
- 배지는 GitHub Actions가 실제로 존재하고 통과할 때만 사용한다.
- Render 무료 인스턴스나 SQLite 초기화 가능성은 “제한” 섹션에 명시한다.

### Track B3 — Unity 보조 카드

- AI 포트폴리오 메인의 주력 카드는 아니다. `C#·Unity 팀 프로젝트` 보조 카드로 둔다.
- 정직한 기여 표현: “팀 멀티플레이 낚시 게임에서 Excel 데이터 관리, 멀티플레이 흐름 통합, 캐릭터 이동 관련 구현, 도감·상점 기능 구현을 담당했습니다.”
- 구현 검증이 끝난 항목만 `검증 완료`라고 쓰고, 2인 접속·낚시 보상·도감 반영·상점 판매 등은 영상/테스트 증거에 맞춰 상태를 갱신한다.

## 7. 인수자 / LLM 실행 순서

1. 이 문서의 0~3절을 읽고, 범위를 넓히지 않는다.
2. Phase 0의 문서와 상태·스키마 계약을 먼저 PR로 만든다.
3. Phase 1 데이터셋 정답과 manifest를 코드보다 먼저 검토한다.
4. Phase 2~4는 각 페이즈의 테스트가 통과한 상태에서만 다음 페이즈로 이동한다.
5. 새 의존성, 외부 API, 실제 문서, 자동 승인 요구가 생기면 구현하지 말고 `docs/decisions/pending.md`에 결정 요청으로 남긴다.
6. 각 PR에는 아래 경계를 쓴다.

```md
문제: <무엇을 해결하는가>
입력/실행 조건: <합성 데이터, 오프라인/외부 API 여부>
관찰 가능한 계약: <사용자가 확인할 결과>
비목표: <이번 PR에서 하지 않는 것>
검증 근거: <명시된 테스트·스크린샷·데모>
```

### 핸드오프 체크리스트

- [ ] 실제 개인정보 또는 실제 고객 문서를 추가하지 않았다.
- [ ] 추출값마다 원문 근거 위치가 있다.
- [ ] blocking 룰은 `HOLD`이고 자동 승인이 없다.
- [ ] 승인/반려에는 사람 별칭과 사유가 있다.
- [ ] 데이터셋·규칙·추출기 버전이 감사 이력에 남는다.
- [ ] 지표에 분모·데이터셋 버전·한계가 적혀 있다.
- [ ] 테스트·평가·Docker 실행법이 README에 있다.
- [ ] 포트폴리오 문구가 테스트/영상 증거보다 강하지 않다.

## 8. 최종 수용 기준 (Ouroboros Seed-ready 형태)

```yaml
goal: >
  합성 한국어 업무 문서를 근거 기반으로 구조화하고 규칙 검증과 사람 승인·감사 이력으로
  안전하게 처리하는 DocumentOps Review Gateway를 포트폴리오용으로 완성한다.

constraints:
  - 실제 개인정보·실제 고객 문서·실제 외부 업무 실행을 사용하지 않는다.
  - 승인·반려는 사람만 수행한다.
  - 기본 경로는 외부 LLM API 키 없이 재현 가능해야 한다.

acceptance_criteria:
  - 합성 평가 데이터와 정답 manifest가 버전·해시와 함께 존재한다.

  - 사람의 승인·반려에 사유가 필요하고 감사 이력이 남는다.
  - 필드 정확도, HOLD 재현율, 오보류율, 근거 유효율, p50/p95가 공개된다.
  - Docker와 GitHub Actions에서 테스트·평가 흐름을 실행할 수 있다.
  - README에 실행법, 한계, 데모, 테스트 증거가 있다.
```
